# Handoff: Government Services Chatbot (state as of 2026-10-15)

For the team taking over the code. When you are done, commit on `feature/gov-chatbot` and tell Claude (the assistant in this repo) what changed so it can re-test with the real model.

## 1. The task (from the organizers' brief)

- Chatbot answering questions about Jordan's **passport, family book, smart ID** (12 service files in `data/`: 3 documents × first issue / renewal / lost / damaged).
- Run: `python main.py questions.json` → writes `answers.json` (same folder). Each message gets `answer` (text) and `contexts` (list of text pieces actually used, from the data).
- **Scoring (automatic, hidden question set, much bigger than the 5-question practice file):**
  1. *Correct answer* (matters most): right amounts/documents/conditions for the user's situation, nothing wrong added; out-of-scope questions declined; unclear ones clarified.
  2. *Right source*: `contexts` come from the service(s) the question is about.
  3. *Grounded*: the answer can be found in `contexts`.
  4. **Time is only a tie-breaker** between teams with equal scores (user's information from the organizers).
- **Rules:** only the provided files as knowledge; every answer generated by the provided model at run time (**`command-r7b-arabic:7b` via Ollama**, no other AI model or online AI service; local embeddings/rerankers are allowed); no pre-written answers; internet is OFF during the run; any build-time tools are fine.
- Question types in the hidden set: simple fact, fee depending on the person (age / expired / abroad / times lost), documents & conditions, facts hidden in notes, comparison, Jordanian dialect, conversation follow-ups (bonus), long stories, wrong assumptions to correct, unclear (ask), not in data (decline).
- Format rules: keep `chats / chat_id / messages / message_id / question` untouched; answer EVERY message (missing = 0); UTF-8; catch errors per message.

- **Required refusal wording: none is mandated.** The brief only says that for questions not in the data the bot "says it doesn't know; invents nothing" (and "says it doesn't have that information instead of inventing an answer"), and that unclear questions get a question asking which document is meant. The only concrete text from the organizers is the reference answer in `answers_example.json` for the flight-ticket question, with `contexts = []`: `عذراً، لا تتوفر لدي معلومات عن أسعار تذاكر الطيران. أستطيع المساعدة في خدمات جواز السفر ودفتر العائلة والبطاقة الذكية فقط.` Answers are compared with a reference answer, so any clear Arabic statement that the bot does not have the information (and what it can help with) is fine. The project owner's original instruction (before the official pack) was the short phrase `لا أعرف`; including both `لا أعرف` and `لا تتوفر لدي معلومات` in a decline covers both.

## 5. Why it fails (34 failing messages: A=14, B=15, C=5)

**A. False declines (14): the single biggest and easiest bucket.** Routing was correct (status ok, right service) but the model answered *"عذراً، لا تتوفر لدي هذه المعلومة في وثائق الخدمة."* even though the fact is in the sources: dev-10, 19, 20, 27, 31, 39, 55, 57, 69-2, 71-2, 71-3, 73-2, 76-2, 78-2.
- Cause (strong evidence): rule 2 of `SYSTEM_ANSWER` in `bot/answer.py` gives the model a ready-made refusal sentence; Command R7B copies it too eagerly, especially for short follow-ups ("الهوية", "وللهوية؟", "وإذا عمري 19…") and some fee questions. The code then accepts any decline under 200 chars (`_is_decline`) and returns it with `contexts=[]`.
- Ideas: if routing status is ok and the model declines, retry once with a different prompt (no ready-made refusal sentence, "the answer is in the sources, find it") and only accept the decline if the retry also declines; for follow-ups rewrite the question into a standalone one in code before sending ("<previous service> + <new question>"); remove the literal refusal sentence from the answer prompt and detect a refusal from a short marker instead.

**B. Wrong or missing fact (15).** Examples (all in `FAILURES.md`):
- dev-08: valid passport (1.5 years left), adult, in Jordan → answered 50, expected 100 (invented "turned 16 by one day"). Check the hints from `bot/facts.py` and the order of the fee lines.
- dev-11: expired + urgent office → answered "100"; expected 50 + 25 = 75.
- dev-12: child 10 years, passport first issue → answered 50, expected 25 (under-16 rule).
- dev-14: lost twice → answered 250 but omitted the bail/كفالة mention.
- dev-22: missing "military service book" in the documents list (answer drops list items); dev-23, 58, 74: partial conditions.
- dev-70-3: follow-up "وإذا كنت برا البلد؟" answered "50 دينار داخل البلاد" (ignored "abroad").
The model picks the wrong fee line when several fee lines have conditions. `bot/facts.py` already precomputes some comparisons; extend it to produce **one explicit "applicable fee line" hint** (the exact sentence from the source plus the computed total) so the model only copies it.

**C. Extra contexts only (5): dev-24, 28, 36, 50, 52.** Answer is fine; `contexts` include another service's text (e.g. `family_book_first_issue` on an ID question) or too many fields. Tighten `_select_contexts` (drop items from services not in the route; require overlap above a threshold).

Also noted: dev-60 (unclear) has an ungrounded number in the clarifying question; dev-73-1 contexts cover the wrong item.

## 6. Priorities (accuracy first)

0. **Finding (checked after the dev run): out-of-scope declines are NOT model-written.** In the dev run all 7 out-of-scope questions returned the fixed template (`_decline_template`, debug `template: decline`). The model does write a valid decline, for example `أنا آسف، لا يمكنني الإجابة على هذا السؤال. أنا متخصص في خدمات دائرة الأحوال المدنية والجوازات…`, but `_is_decline` in `bot/answer.py` only accepts the words in `DECLINE_WORDS` (عذرا, لا تتوفر, لا املك, ليس لدي…), so the model's text is rejected every time. Fix: add the wording the model really uses (آسف, لا يمكنني, متخصص…) to `DECLINE_WORDS`, then re-check that no decline is rejected. This also removes the risk against the rule that every answer must be generated by the model. The same kind of check exists for clarifying questions (must contain a question mark and no numbers).

1. Fix bucket A (false declines): expected to move several types at once, especially conversation and fee.
2. Fix fee-line selection (bucket B): extend `bot/facts.py` hints; make the answer prompt copy the hinted line.
3. Follow-up handling: standalone rewrite or stronger inheritance of the previous service + situation (conversation is a bonus category: it can only add points, never lower the main score).
4. Tighten `contexts` (bucket C): improves "right source" / "grounded" scores.
5. Only then speed: shorter prompts (core fields are always sent), skip the classification call when the router is certain, fewer retries. Parallel chats help only if Ollama is started with `OLLAMA_NUM_PARALLEL≥2`, which we do not control on the judging machine. Realistic floor ≈ 3–5 s per question (one model call, short answer); realistic good average 5–7 s. Do not trade accuracy for time.

## 8. Open questions / risks

- `bot/answer.py` has an **extractive fallback** (copies source text) when the model returns nothing, and fixed decline/clarify templates when the model's text is rejected. Ask the organizers whether this fits "every answer must be generated by the model"; it only triggers on model failure (7 templated declines in the dev run, all out-of-scope).
- The hidden set is much bigger: at ~11 s/question, 200 questions ≈ 38 min. Unknown time limit.
- The 12 data files and the practice `questions.json`/`answers_example.json` are committed to the (GitHub) repo because `main.py` needs them. The brief PDF and `participant_pack/` are git-ignored. Make the repo private if the organizers do not want the data public.
- The dev set was written by the original authors and routing was tuned on it, so routing scores on it are optimistic; the answer-stage scores above are a first measurement and are real.
