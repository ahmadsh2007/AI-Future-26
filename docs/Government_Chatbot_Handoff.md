# 1. Everything the project owner told us (instructions and constraints)

- 4-hour hackathon; build a RAG document Q&A system that can be plugged into the real model and documents on the day.
- Model: a lightweight ~7B LLM (revealed at the event). Data: 20 to 30 Arabic documents (PDF/TXT). Questions and answers must be in Arabic.
- Main goal: maximize accuracy and strictly prevent hallucinations. If the answer is not explicitly in the retrieved context, answer "لا أعرف" and nothing else.
- Wanted: modular, easy-to-debug Python; version control on a new branch; test data pipeline using an Arabic financial news dataset; README with exact commands.
- Second request: validate everything (LLM-level refusal, Arabic PDF text direction, English prompt mode, reranker, openai/hf backends, calibration, e5-large vs bge-m3 thresholds) with an automated runner; update the README with results. Result: 42 of 42 tests passed (see section 4).

# 2. The challenge (summary of the organizers' brief)

- Build a chatbot that answers citizens' questions about Jordan's passport, family book and smart ID, correctly and only from the official documents. Time: 4 hours, teams of 3 to 4. Same ~7B model for all teams via Ollama.
- Data: 12 text files in data/, one per service: 3 documents (passport, family book, smart ID) times 4 situations (first issue, renewal, lost, damaged). Each file has 9 fields: beneficiaries, where to apply, conditions, documents required, procedure, time, partners, notes, fees. The text is raw website text with menus, tabs, typos, duplicates and numbers written both as digits and words.
- What makes it hard: fees depend on the person (age, expired or not, inside or outside Jordan, number of times lost); the four files per document are near-identical (wrong file means a convincing but wrong answer); users write dialect (باسبور، الهوية، قديش…); facts hide in notes; small models make reasoning mistakes and the default context window is small; some questions are not covered and the bot must say it does not know; unclear questions need a clarifying question.
- Hidden test types: simple fact; fee depending on the situation; documents or conditions list; fact hidden in notes; comparison between two services; dialect; conversation follow-up (bonus); long story with several people; wrong assumption to correct; unclear request; not in the data.
- Run command used by the judges: python main.py questions.json, offline, on the team's laptop. It must write answers.json in the same folder.
- answers.json format: keep chats, chat_id, messages, message_id, question exactly; add "answer" (text the user reads) and "contexts" (list of text pieces from the data that were actually used; [] when nothing). Answer every message (missing = zero). Valid JSON, UTF-8, per-message error handling. Write answers into the same chat and message; never reorder or merge. Every chat is a new user (forget the previous chat).
- Evaluation criteria: (1) Correct answer: right amounts, documents and conditions for the user's situation, nothing wrong added; out-of-scope declined; unclear clarified. This matters most. (2) Right source: contexts come from the service(s) the question is about. (3) Grounded answer: what the answer says can be found in the contexts; model-memory answers count as unsupported. Also a short walkthrough: how data was handled, how the bot finds the right information, how it avoids making things up.
- Rules: only the provided files as knowledge; answers generated by the provided model at run time; no pre-written answers; no other AI models or online AI services; any tools while building; cleaning data allowed but facts must not change; local embeddings/rerankers allowed; internet off during the run so everything must be downloaded beforehand.

## Pipeline of the working bot

- bot/kb.py cleans and parses the 12 files into the 9 fields. Menu lines removed, numbering unified, clear typos fixed, one duplicate removed, number words get digits added (e.g. "ثلاثة أشهر (3)"). A check confirms no raw number or word was lost; every change is logged in kb/cleaning_log.txt.
- bot/router.py picks the service file(s) with code, not the model (regex plus dialect families; handles comparisons and long stories; trap words such as "دفتر خدمة العلم" and "بطاقة الجسور"; asks when document or situation is missing; declines topics not in the data; chat memory for follow-ups).
- bot/facts.py reads the user's situation (age, days left on the passport, inside or outside Jordan, times lost, urgent office, military) and precomputes the comparisons as plain hints for the model.
- bot/answer.py builds the prompt (only the chosen service's fields, notes always included), calls the model at temperature 0, checks that every number in the answer comes from the sources, the question, the hints or a sum of two source numbers (one retry otherwise), then selects the contexts by word and number overlap. Declines and clarifying questions are written by the model and rejected if they contain numbers. A fixed template is used only if the model fails. If the model returns nothing, short answers are copied from the documents (extractive fallback).
- main.py: one try/except per message, every message pre-filled with "error", answers.json saved after every chat, UTF-8 everywhere. Flags: --debug (adds route and timing), --out PATH, --dry-run (no model).
- tests/ holds 224 unit tests that do not need a model. eval/ holds the 90-message dev set, the scorer (score.py) and helper scripts.

# 4. Environment and earlier test history

- Machine: MacBook with Apple GPU. Python 3.9 or newer works (standard library only). Ollama must be running (ollama serve or the desktop app).
- Model: command-r7b-arabic:7b, 8.0B parameters, Q4_K_M, 5.1 GB, max context 16384 (the bot uses num_ctx 8192), license CC-BY-NC. ollama show lists only "completion" and "tools" capabilities: there is NO thinking mode, so accuracy must come from prompt and code. It runs 100% on the GPU and stays loaded for 30 minutes (keep_alive).
- It is now the only model in Ollama. Before the evaluation: turn Wi-Fi off and run python main.py questions.json once.
- First-phase pipeline (generic RAG, archived): bge-m3 embeddings (also e5-large tested), ChromaDB, similarity threshold gate, constrained prompts. 42 of 42 automated tests passed on qwen2.5:7b and qwen3:8b: threshold filtering, LLM refusal and post-processing, Arabic PDF extraction (a reversed-words and reversed-digits bug in PyMuPDF output was found and fixed), backends (ollama, openai, hf, reranker). Thresholds measured: bge-m3 0.55 (off-topic <= 0.51, real 0.62 to 0.93), e5-large 0.80.
- Our first government bot on qwen3:8b: 31 of 32 own dev questions passed after fixes (fee questions used thinking mode, about 20 s each). Found and fixed: thinking running out of tokens produced a false decline; "لأول مرة" next to "ضاع" means first loss, not first issue. These results do not carry over to command-r7b.

# 7. Why it fails and what to change (accuracy first)

## Priority 1: false declines (bucket A, 14 messages)

- Evidence: routing status was ok with the correct service in every case, yet the model returned the sentence "عذراً، لا تتوفر لدي هذه المعلومة في وثائق الخدمة." Rule 2 of SYSTEM_ANSWER in bot/answer.py hands the model that exact sentence, and Command R7B copies it too eagerly, especially for short follow-ups ("الهوية", "وللهوية؟", "وإذا عمري 19 وما طلعتها لهلأ؟") and for some fee questions (dev-10, 19, 20, 27).
- The code accepts any decline shorter than 200 characters (_is_decline) and returns it with contexts = [].
- Ideas: when routing is ok and the model declines, retry once with a prompt that has no ready-made refusal sentence and says the answer is in the sources; accept the decline only if the retry also declines. For follow-ups rewrite the question into a standalone one in code ("<service> + new question") before the model sees it. Replace the literal refusal sentence in the prompt with a short marker the code detects.

## Priority 2: choosing the right fee line (bucket B)

- Failures: dev-08 (valid passport, adult, in Jordan: answered 50, expected 100); dev-11 (expired plus urgent office: answered 100, expected 50 + 25 = 75); dev-12 (child of 10, first issue: answered 50, expected 25); dev-14 (lost twice: omitted the bail/كفالة); dev-70-3 (follow-up "and abroad?" ignored).
- Idea: extend bot/facts.py to output one explicit "applicable fee line" hint (the exact source sentence plus the computed total) so the model only copies it. Include list items completely for documents and conditions questions (dev-22, 23, 58, 74 lost items).

## Priority 3: conversation follow-ups (bonus category)

- Conversation scored 41.7. Follow-ups can only add points, never lower the main score. Make sure the inherited service and situation are applied in the prompt and in the fee hints (dev-69-2, 70-3, 71-2, 71-3, 73-2, 76-2, 78-2).

## Priority 4: contexts precision (bucket C and parts of A/B)

- dev-24, 28, 36, 50, 52 return extra items or another service's text (e.g. family_book_first_issue on an ID question). Drop items from services not in the route and require a minimum overlap with the answer.

## Priority 5: speed (only after accuracy)

- Shorter prompts (core fields are always sent), skip the classification model call when the router is certain, fewer retries. Parallel chats only help if Ollama runs with OLLAMA_NUM_PARALLEL of 2 or more, which we do not control on the judging machine. Realistic floor 3 to 5 s per question; a good average 5 to 7 s. Never trade accuracy for time.

# 8. Do not break, open questions and commands

## Do not break

- The answers.json format and the "answer every message" behavior (per-message try/except, partial file after every chat).
- Offline operation: nothing except local Ollama at 127.0.0.1:11434.
- Declines and clarifying questions stay model-generated (templates only when the model fails).
- Keep the 224 tests green; after each change re-run the 90-question test and compare with eval/results/2026-10-15_command-r7b/score_report.txt (baseline overall 70.0).

## Open questions and risks

- The extractive fallback (copies source text when the model returns nothing) and the fixed templates: ask the organizers whether they fit "every answer must be generated by the provided model". They only trigger on model failure.
- The 12 data files and the practice questions.json / answers_example.json are committed to the GitHub repo because main.py needs them. The brief PDF and participant_pack/ are git-ignored. Make the repo private if the organizers do not want the data public.
- The 90-question dev set was written by the original authors and the router was tuned on it, so routing scores on it are optimistic. The answer-stage scores are a first real measurement.
- Hidden test set is much larger than the practice file; the time limit is unknown.
